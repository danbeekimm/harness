# DB 규칙

쿼리, 매퍼, 엔티티, 마이그레이션을 쓰거나 고칠 때 따른다. DBMS와 데이터 접근 방식은 프로필의 `스택`을 따른다. 대상 경로가 프로젝트와 다르면 위 `paths`를 고친다.

## 쿼리

- 값은 바인딩한다. 문자열 결합으로 쿼리를 만들지 않는다. MyBatis에서는 `#{}`를 쓰고 `${}`는 쓰지 않는다. 정렬 컬럼처럼 바인딩할 수 없는 것은 허용 목록으로 검증한 뒤에만 쓴다.
- `SELECT *`를 쓰지 않는다. 필요한 컬럼을 적는다.
- 목록 조회에는 정렬 기준과 페이징을 둔다. 정렬 기준은 결과 순서가 하나로 정해지게 한다(동률이면 키를 덧붙인다).
- `UPDATE`, `DELETE`에는 조건이 있어야 한다. 조건이 비어 전체가 바뀔 수 있는 동적 쿼리를 만들지 않는다.
- 반복문 안에서 쿼리를 실행하지 않는다. 한 번에 가져오거나 배치로 처리한다.
- 조건에 쓰는 컬럼에 함수를 씌우거나 앞쪽 와일드카드(`LIKE '%값'`)를 쓰면 인덱스를 타지 못한다. 대량 테이블에서는 피한다.

## JPA를 쓰는 프로젝트

- 연관 관계는 지연 로딩이 기본이다. 필요한 곳에서 fetch join이나 `@EntityGraph`로 가져온다.
- 컬렉션을 fetch join하면서 페이징하지 않는다.
- 엔티티를 컨트롤러 밖으로 내보내지 않는다. DTO로 바꾼다.
- 벌크 연산 뒤에는 영속성 컨텍스트가 실제 데이터와 달라진다. 이어서 같은 엔티티를 쓰면 비우고 다시 읽는다.

## 스키마 변경

- 스키마는 마이그레이션 파일로만 바꾼다. 형식과 위치는 프로필의 `스택`, `디렉터리`를 따른다. DB에 직접 DDL을 실행하지 않는다.
- 이미 적용된 마이그레이션 파일은 고치지 않는다. 새 파일을 추가한다.
- 배포 중에는 이전 버전 서버와 새 스키마가 함께 돈다. 컬럼 삭제·이름 변경·`NOT NULL` 추가는 그 상태에서도 깨지지 않게 단계를 나눈다.
- 기존 행이 있는 테이블에 `NOT NULL` 컬럼을 추가할 때는 기본값이나 채우는 단계를 둔다.
- 조건·조인·정렬에 새로 쓰이는 컬럼은 인덱스가 필요한지 본다. 대량 테이블의 인덱스 추가는 잠금 영향을 보고에 적는다.
- 데이터를 지우거나 덮어쓰는 마이그레이션은 계획 문서의 `의도된 변경`에 있어야 한다. 없으면 멈추고 보고한다.

## 실행

- 개발·운영 DB의 데이터와 구조를 직접 바꾸지 않는다. 스키마 확인과 조회는 `db-helper`에 맡긴다.
- 접속은 프로필의 `DB 접속`에 적힌 방법만 쓴다.
