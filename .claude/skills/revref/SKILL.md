# revref: 두 관점 리뷰와 반영

인자: `$ARGUMENTS`

## 0. 시작 전 확인

1. **미결 사항이 있으면 리뷰하지 않는다.** 작업 중에 사용자의 결정이 필요한 문제가 남아 있으면(계획 문서 `미결 사항`에 체크 안 된 항목, 구현하면서 생긴 질문) 리뷰를 보류하고 그것부터 보고한다. 결정에 따라 코드가 바뀌므로 지금 리뷰하면 다시 해야 한다.
2. **범위를 정한다.**
   - 인자가 slug면 계획 문서는 `docs/plans/<slug>/plan.md`이고, 범위는 그 문서 `진행 기록`의 시작 커밋부터 `HEAD`까지다.
   - 인자가 커밋 범위나 파일 목록이면 그대로 쓴다.
   - 인자가 없으면 `status`가 `in-progress`인 계획을 찾는다. 하나면 그것을 쓰고, 없거나 여럿이면 사용자에게 묻는다.
3. **작업 트리가 깨끗한지 본다.** 커밋되지 않은 변경이 있으면 범위에 넣을지 사용자에게 묻는다.
4. `.claude/rules/project-profile.md`의 `명령`에서 빌드·테스트 명령을 확인한다.

## 1. 라운드

한 라운드는 아래 순서다. 최대 5라운드.

### 1-1. 두 패스를 동시에 실행

`code-reviewer`와 `refactoring-specialist`를 **한 메시지에서 동시에** 호출한다. 프롬프트에는 다음만 넣는다.

```
리뷰 범위: <base>..HEAD   (또는 파일 목록)
계획 문서: docs/plans/<slug>/plan.md   (없으면 "없음")
```

2라운드부터는 범위를 **직전 라운드에서 반영한 커밋들**로 좁힌다. 이미 본 코드를 다시 보게 하지 않는다.

지킬 것:

- 범위를 정확히 준다. "최근 변경"처럼 에이전트가 범위를 추측해야 하는 표현을 쓰지 않는다.
- 한 에이전트의 결과를 다른 에이전트에게 넘기지 않는다. 이전 라운드의 지적 내용, 메인 세션의 의견, 예상되는 문제도 넘기지 않는다. 두 패스는 서로 모르는 상태로 본다.
- 한 패스가 실패하면 그 패스만 다시 호출한다.

### 1-2. 지적 분류

두 결과를 받아 항목마다 하나로 분류한다.

| 분류 | 기준 | 처리 |
|------|------|------|
| 반영 | 코드에서 확인해 보니 맞다 | 고친다 |
| 반영 안 함 | 확인해 보니 사실이 아니다(False Positive), 계획 문서의 의도된 변경이다, 범위 밖이다 | 이유를 적고 넘어간다 |
| 미결 | 맞는지는 사용자의 결정에 달렸다 | 고치지 않고 보고 대상에 올린다 |

- `[P0]`, `[P1]`은 반영 안 함으로 넘기려면 코드로 확인한 반증이 있어야 한다. 반증이 없으면 반영하거나 미결로 올린다.
- `[P3]`과 리팩터링 제안은 이번 변경 범위 안에서 끝나는 것만 반영한다.
- 두 패스가 같은 곳을 다르게 고치라고 하면 결함 쪽을 따른다.
- 리뷰어의 지적을 그대로 믿지 않는다. 반영하기 전에 해당 코드를 직접 읽어 확인한다.

### 1-3. 반영과 커밋

- **항목 하나를 고칠 때마다 커밋한다.** 여러 지적을 한 커밋에 섞지 않는다. 같은 원인의 지적 둘은 한 커밋으로 묶어도 된다.
- 커밋 메시지: `review(<slug>): <지적 번호> <한 줄 요약>` 예: `review(order-cancel): P1 취소 중복 요청 시 이중 환불 방지`
- 반영이 끝나면 프로필의 빌드·테스트 명령을 실행한다. 실패하면 고치고 그 수정도 커밋한다.

### 1-4. 종료 조건

다음 중 하나면 라운드를 끝낸다.

1. 이번 라운드에서 반영한 항목이 없다(두 패스 모두 지적이 없거나, 전부 반영 안 함이다).
2. 이번 라운드에서 반영한 것이 `[P3]`과 리팩터링 제안뿐이다. 다시 볼 필요가 없다.
3. 미결 항목이 생겼다. 반영할 수 있는 나머지는 반영하고 끝낸다.
4. 5라운드를 마쳤다.

그 밖에는 다음 라운드로 간다.

## 2. 보고

아래 순서로 보고한다. 해당 사항이 없는 절은 "없음"으로 적는다.

1. **미결 사항**: 사용자가 정해야 하는 것. 선택지와 권장안.
2. **남은 지적**: 5라운드를 채우고도 남은 `[P0]`~`[P2]`. 있으면 완료가 아니다.
3. **반영한 것**: 지적 번호, 한 줄 요약, 커밋 해시.
4. **반영하지 않은 것**: 지적 번호와 이유(False Positive, 의도된 변경, 범위 밖).
5. **검증**: 실행한 빌드·테스트 명령과 결과. 실패가 있으면 출력의 핵심 줄.
6. **라운드 수**

계획 문서가 있으면 `진행 기록`에 라운드 수, 반영하지 않은 지적과 이유, 검증 결과를 덧붙인다.

## 하지 않는 것

- 푸시하지 않는다. `--amend`로 커밋을 고쳐 쓰지 않는다.
- 리뷰어가 지적하지 않은 곳을 이 단계에서 새로 고치지 않는다.
- 테스트를 지우거나 단언을 약하게 만들어 통과시키지 않는다.
