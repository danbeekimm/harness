# /verify: 수용 기준 E2E 검증

인자: `$ARGUMENTS`

## 1. 진입 조건

`docs/plans/<slug>/plan.md`를 읽고 확인한다. 어긋나면 시작하지 않고 이유를 보고한다.

| 확인 | 조건 | 어긋날 때 |
|------|------|-----------|
| `status` | `implemented` | `ready`·`in-progress`면 `/dev <slug>`를 안내한다. `verified`면 이미 끝났다고 알리고, 다시 검증할지 묻는다 |
| 미결 사항 | 체크 안 된 항목 0건 | `/plan <slug>`로 돌려보낸다 |
| E2E 준비 | 프로필의 `E2E`가 채워져 있고 E2E 디렉터리가 있다 | `/init-harness`를 안내한다 |
| 작업 트리 | 커밋되지 않은 변경이 없다 | 사용자에게 묻는다 |

## 2. 1차 검증

`tester` 에이전트를 호출한다. 프롬프트:

```
계획 문서: docs/plans/<slug>/plan.md
```

결과를 받으면 tester가 쓴 테스트 파일을 커밋한다. 메시지: `test(<slug>): 수용 기준 E2E`

- 모두 통과면 4단계로 간다.
- 실패나 미작성이 있으면 3단계로 간다.

## 3. 수정과 2차 검증

실패 항목을 `판단`에 따라 처리한다.

| tester의 판단 | 처리 |
|---------------|------|
| 애플리케이션 결함 | 원인을 찾아 고치고 단위·통합 테스트를 실행한 뒤 커밋한다. 메시지: `fix(<slug>): AC-<n> <요약>` |
| 수용 기준 모호 | 고치지 않는다. 계획 문서 `미결 사항`에 추가하고 보고 대상에 올린다 |
| 환경 문제 | 서버 기동, 테스트 데이터, 계정을 확인한다. 프로필의 방법으로 해결되지 않으면 보고 대상에 올린다 |

고친 것이 있으면 `tester`를 **한 번 더** 호출한다. 프롬프트에 실패했던 수용 기준 번호와 반영한 수정 요약을 넣는다.

```
계획 문서: docs/plans/<slug>/plan.md
재실행: 이전 실패 AC-2, AC-5
반영한 수정: <커밋별 한 줄>
```

**tester 호출은 계획 하나에 최대 2회다.** 2차에서도 실패가 남으면 더 고치지 않고 그대로 보고한다. 세 번째 호출로 넘어가지 않는다.

애플리케이션 코드를 고쳤다면 변경이 작아도 프로필의 전체 테스트 명령을 실행한다. 수정이 크면(여러 파일, 로직 변경) `revref`를 고친 커밋 범위로 실행한다.

## 4. 상태 변경과 보고

수용 기준이 **모두 통과**했고 미결 사항이 0건이면 `status: verified`로 바꾼다. 아니면 `implemented`로 둔다.

계획 문서 `진행 기록`에 검증 결과(실행 횟수, 통과·실패 수, 실패 항목)를 적고 커밋한다. 메시지: `plan(<slug>): 검증 완료` 또는 `plan(<slug>): 검증 결과 기록`

보고 순서:

1. 미결 사항(있으면 맨 먼저)
2. 실패한 수용 기준: 기대, 실제, 단서(trace·스크린샷 경로)
3. 통과한 수용 기준 수 / 전체
4. 검증 중 고친 것과 커밋 해시
5. tester 실행 횟수, 실행한 명령
6. 다음 단계: `verified`면 사용자가 검토 후 푸시. 아니면 무엇이 정해지거나 고쳐져야 하는지

## 하지 않는 것

- 통과시키려고 테스트의 단언을 약하게 만들거나 테스트를 건너뛰게 하지 않는다.
- 수용 기준을 구현에 맞춰 고치지 않는다. 수용 기준이 틀렸다고 판단되면 미결 사항으로 올린다.
- 푸시하지 않는다.
