# /dev: 계획 문서 → 구현 → 리뷰 → 보고

인자: `$ARGUMENTS`

## 1. 진입 조건

`docs/plans/<slug>/plan.md`를 읽고 확인한다. 하나라도 어긋나면 **시작하지 않고** 이유를 보고한다.

| 확인 | 조건 | 어긋날 때 |
|------|------|-----------|
| `status` | `ready` 또는 `in-progress` | `draft`면 `/plan <slug>`로 돌려보낸다. `implemented`면 `/verify <slug>`를 안내한다 |
| 미결 사항 | 체크 안 된 항목 0건 | 남은 항목을 보여 주고 `/plan <slug>`로 돌려보낸다 |
| 프로필 | `.claude/rules/project-profile.md`에 `<미입력>`이 없다 | `/init-harness`를 안내한다 |
| 작업 트리 | 커밋되지 않은 변경이 없다 | 무엇이 남아 있는지 보여 주고 사용자에게 묻는다 |

인자가 없으면 `ready`나 `in-progress`인 계획을 찾는다. 하나면 그것을 쓰고, 여럿이면 묻는다.

`status`가 `ready`면 `in-progress`로 바꾸고, `진행 기록`에 시작 커밋(`git rev-parse HEAD`)과 날짜를 적은 뒤 커밋한다. 메시지: `plan(<slug>): 개발 시작`

`in-progress`로 들어왔으면 `작업 목록`에서 체크 안 된 첫 항목부터 이어서 한다.

## 2. 작업 단위 구현

`작업 목록`을 위에서 아래로 진행한다. 항목 하나마다:

1. 관련 수용 기준과 결정 사항을 다시 읽는다.
2. 구현한다. 프로필의 `재사용 우선 대상`에 같은 기능이 있는지 먼저 찾는다. 파일 종류별 규칙(`.claude/rules/`)을 따른다.
3. 이 작업의 테스트를 쓴다(`.claude/rules/test.md`).
4. 프로필의 빌드·테스트 명령을 실행한다. 실패하면 고친다.
5. 계획 문서에서 이 항목을 `[x]`로 바꾼다.
6. **커밋한다.** 코드와 계획 문서의 체크 표시를 한 커밋에 넣는다. 메시지: `feat(<slug>): T<n> <한 줄 요약>` (성격에 따라 `fix`, `refactor`, `test`, `chore`)

지킬 것:

- 작업 하나가 커밋 하나다. 여러 작업을 한 커밋에 섞지 않는다. 계획에 없는 수정을 끼워 넣지 않는다.
- 스키마·데이터 확인은 `db-helper`에 맡긴다. DB를 직접 바꾸지 않는다. 마이그레이션은 파일로 쓴다.
- 푸시하지 않는다. `--amend`를 쓰지 않는다.

### 멈추고 보고하는 경우 (보고 우선)

다음이 생기면 **그 작업을 진행하지 않고** 보고한다. 추측으로 넘어가지 않는다.

- 계획 문서에 답이 없는 결정이 필요하다
- 계획 문서와 실제 코드·스키마가 어긋나 작업 목록대로 할 수 없다
- 수용 기준끼리 충돌한다
- 금지 경로의 파일을 읽거나 고쳐야 한다
- 같은 실패를 세 번 고쳐도 해결되지 않는다

이때 계획 문서 `미결 사항`에 항목을 추가하고 커밋한 뒤(`plan(<slug>): 미결 사항 추가`), 이미 끝낸 작업과 함께 보고한다. `status`는 `in-progress`로 둔다. 리뷰 단계로 넘어가지 않는다.

## 3. 리뷰

작업 목록이 모두 `[x]`가 되면 `revref` 스킬을 `<slug>`로 실행한다. 범위는 `진행 기록`의 시작 커밋부터 `HEAD`까지다.

revref가 미결 사항을 올리면 여기서 멈추고 보고한다.

## 4. 최종 테스트

리뷰 반영이 끝난 상태에서 프로필의 전체 빌드·테스트 명령을 한 번 더 실행한다. 실패가 남아 있으면 완료가 아니다.

## 5. 상태 변경과 보고

다음을 모두 만족하면 `status: implemented`로 바꾸고 커밋한다(`plan(<slug>): 구현 완료`).

- 작업 목록이 모두 `[x]`
- 미결 사항 0건
- 남은 `[P0]`~`[P2]` 지적 없음
- 전체 빌드·테스트 통과

하나라도 아니면 `in-progress`로 두고 무엇이 남았는지 보고한다.

보고 순서:

1. 미결 사항(있으면 맨 먼저)
2. 실패한 것, 남은 지적, 건너뛴 것
3. 끝낸 작업과 커밋 해시
4. 리뷰 결과 요약(라운드 수, 반영, 반영하지 않은 것과 이유)
5. 실행한 테스트 명령과 결과
6. 다음 단계: `implemented`면 `/verify <slug>`

통과하지 못한 것을 통과했다고 쓰지 않는다. 실행하지 않은 검증을 했다고 쓰지 않는다.
