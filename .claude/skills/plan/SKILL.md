# /plan: 기획안 → 계획 문서

인자: `$ARGUMENTS`

이 스킬은 계획 문서만 만든다. 애플리케이션 코드는 쓰지 않는다. 구현은 **다른 세션**에서 `/dev <slug>`로 한다.

## 1. 대상 정하기

- 인자가 `docs/plans/`에 이미 있는 slug면 그 계획 문서를 이어서 다듬는다(4단계부터).
- 인자가 파일 경로면 새 계획을 만든다.
- 인자가 없으면 기획 내용을 어디서 가져올지 사용자에게 묻는다.

새 계획의 slug는 영문 소문자와 하이픈으로 짧게 짓는다(예: `order-cancel`). 같은 이름이 있으면 사용자에게 묻는다.

## 2. 기획안 읽기

- xlsx, pptx, docx, pdf는 텍스트로 추출해서 읽는다. Windows에서 `python3`이 없으면 `python`을 쓴다.

  ```
  python3 .claude/scripts/extract_spec.py <파일> -o docs/plans/<slug>/spec.txt
  ```

- 텍스트·마크다운 파일은 그대로 읽는다.
- 추출 결과가 비었거나 "이미지로만 들어 있을 수 있다"는 경고가 나오면, 화면 설계가 이미지인 것이다. 추측하지 말고 사용자에게 알리고 이미지 파일이나 설명을 요청한다.
- 추출에 실패하면(도구 없음, 파일 손상) 오류 메시지를 그대로 보고하고 멈춘다.

## 3. 코드 파악

`.claude/rules/project-profile.md`를 읽고, 기획안이 건드리는 화면·API·테이블이 지금 코드에서 어떻게 되어 있는지 본다.

- 프로필이 채워지지 않았으면(`<미입력>`이 남아 있으면) 멈추고 `/init-harness`를 먼저 실행하라고 알린다.
- 넓게 찾아봐야 하면 Explore 에이전트에 맡긴다.
- 스키마나 실제 데이터 형태를 확인해야 하면 `db-helper`에 맡긴다.

## 4. 계획 문서 작성

`docs/plans/_template/plan.md`를 `docs/plans/<slug>/plan.md`로 복사해 채운다. 템플릿의 안내 주석은 지운다.

- **수용 기준**: 사용자 관점에서 관찰할 수 있는 문장. `/verify`가 항목마다 E2E 시나리오를 만든다. "잘 동작한다" 같은 문장은 쓰지 않는다.
- **범위의 제외**: 기획안에 있지만 이번에 하지 않는 것을 적는다.
- **작업 목록**: 한 항목이 커밋 하나가 되도록 쪼갠다. 항목마다 관련 수용 기준 번호를 붙인다. 순서는 의존 관계를 따른다(스키마 → 서버 → 화면). 각 항목에 테스트가 들어간다.
- **의도된 변경**: 기존 동작을 바꾸거나 지우는 것. 리뷰어가 결함으로 오해하지 않도록 적는다.
- **미결 사항**: 기획안과 코드만으로 정할 수 없는 것. 아래 기준으로 뽑는다.

### 미결 사항으로 올리는 것

- 기획안에 없거나 서로 어긋나는 동작(예외 상황, 권한별 차이, 빈 값·경계값 처리)
- 기획안과 현재 코드·스키마가 충돌하는 것
- 기존 데이터의 처리(마이그레이션, 기본값)
- 구현 방식이 둘 이상이고 사용자에게 보이는 결과나 비용이 달라지는 것

구현 세부(클래스 이름, 내부 구조)는 질문하지 않는다. 프로필과 규칙 파일을 따라 정한다.

**추측으로 채우지 않는다.** 그럴듯한 답이 있어도 사용자가 정할 일이면 미결로 둔다. 항목마다 선택지와 권장안, 권장 이유를 적는다.

## 5. 결정 질문

미결 사항을 사용자에게 묻는다. 한 번에 4개까지 묻고, 선택지와 권장안을 함께 낸다.

- 답이 나온 항목은 `미결 사항`에서 지우고 `결정 사항`에 옮긴다(결정자, 날짜 포함).
- 답에 따라 수용 기준과 작업 목록을 고친다.
- 답이 새 질문을 만들면 미결 사항에 추가하고 다시 묻는다.
- 사용자가 지금 답할 수 없다고 하면 미결로 남겨 두고 `draft`로 끝낸다.

## 6. 상태 정하기

- `미결 사항`에 체크 안 된 항목이 **0건**이고 수용 기준과 작업 목록이 채워졌으면 `status: ready`로 바꾼다.
- 하나라도 남았으면 `status: draft`로 둔다. `/dev`는 `draft`에서 시작하지 않는다.

## 7. 커밋과 보고

계획 문서(와 `spec.txt`)를 커밋한다. 메시지: `plan(<slug>): <제목>` 또는 `plan(<slug>): 결정 사항 반영`

보고 순서:

1. 남은 미결 사항(있으면 맨 먼저)
2. 계획 문서 경로와 `status`
3. 수용 기준 수, 작업 수
4. 다음 단계: `ready`면 "새 세션에서 `/dev <slug>`", `draft`면 "미결 사항이 정해지면 `/plan <slug>`"
